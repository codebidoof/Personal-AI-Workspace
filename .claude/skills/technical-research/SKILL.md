# Technical Research

기술 주제를 조사하고 재사용할 수 있는 형태로 정리한다.

## 원칙

1. **공식 문서 우선**: 공식 문서, 공식 블로그, 릴리스 노트, 공식 저장소(README, CHANGELOG, 소스)를 가장 먼저 확인한다.
2. **최신 자료 우선**: 같은 수준의 자료라면 더 최신 자료를 따른다. 학습된 지식은 오래되었을 수 있으므로 기억만으로 답하지 않고 현재 기준을 확인한다.
3. **출처 없는 주장 금지**: 확인하지 못한 내용은 사실처럼 쓰지 않고 "확인하지 못함"이라고 적는다.

## 절차

1. **범위 파악**: 무엇을 알고 싶은지, 어떤 프로젝트와 버전에 적용할지 정한다. 모호하면 먼저 묻는다.
2. **기존 지식 확인**: `knowledge/<기술>/`에 같은 주제가 있는지 확인한다. 있으면 출발점으로 쓰되, 최신성은 다시 검증한다.
3. **공식 문서 확인**: 공식 문서에서 현재 안정(stable) 버전 기준의 내용을 찾는다. 문서의 버전과 날짜를 함께 기록한다.
4. **최신 동향 확인**: 릴리스 노트와 변경 이력에서 최근 변경, deprecated, breaking change를 확인한다.
5. **보조 자료 확인**: 공식 문서로 부족할 때만 컨퍼런스 발표, 신뢰할 수 있는 개인·기업 블로그, 이슈 트래커, Stack Overflow 등을 본다.
6. **교차 검증**: 서로 다른 자료가 충돌하면 공식 문서와 더 최신 자료를 따르고, 충돌 사실과 이유를 함께 적는다.
7. **정리**: 아래 출력 형식으로 작성한다.

## 자료 우선순위

| 순위 | 자료 | 비고 |
|---|---|---|
| 1 | 공식 문서, 릴리스 노트, 공식 저장소 | 항상 먼저 확인 |
| 2 | 공식 채널의 발표·블로그·샘플 | 공식 문서를 보완 |
| 3 | 신뢰할 수 있는 개인·기업 기술 블로그, 컨퍼런스 발표 | 작성일과 대상 버전을 확인 |
| 4 | 커뮤니티 Q&A, 포럼 | 참고용. 단독 근거로 쓰지 않는다 |

최신성 기준:
- 같은 순위 안에서는 최신 자료를 우선한다.
- 순위가 낮아도 공식 문서가 아직 반영하지 못한 최신 변경을 다루고 있다면 참고할 수 있다. 이때는 공식 문서와의 차이를 명시한다.
- 대상 버전을 알 수 없거나 2년 이상 지난 자료는 그 사실을 표시하고, 최신 공식 문서로 다시 확인한다.

## 출력 형식

```markdown
# <주제>

- 기준 버전: <라이브러리/프레임워크 버전>
- 조사일: <YYYY-MM-DD>

## 요약
<핵심 결론 3~5줄>

## 내용
<개념, 사용법, 예시 코드, 주의점>

## 최신 변경 사항
<최근 버전에서 바뀐 점, deprecated, breaking change>

## 출처
| 자료 | 종류 | 버전/작성일 |
|---|---|---|
| [제목](URL) | 공식 문서 | v1.2 / 2026-09 |
```

- 코드 예시는 기준 버전에서 동작하는 것만 쓴다.
- 확실하지 않은 부분은 "확인 필요"로 표시한다.
- 사용자의 프로젝트에 적용할 때는 프로젝트의 실제 의존성 버전과 기준 버전이 일치하는지 확인한다.

## 저장

- 기본적으로 조사 결과는 답변으로 전달한다.
- 사용자가 저장을 원하면 `knowledge/<기술>/`에 Obsidian 노트로 저장한다. 파일 이름은 주제를 알 수 있게 짓는다.
- 같은 주제의 노트가 이미 있으면 새로 만들지 않고 갱신을 제안한다. 기존 내용을 임의로 삭제하지 않는다.
- 조사 중 AI가 틀린 정보를 쓴 사실이 드러나면 `wiki/mistakes/`에 기록할지 제안한다.
