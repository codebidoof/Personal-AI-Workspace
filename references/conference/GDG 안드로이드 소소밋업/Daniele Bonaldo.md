# **제약 없는 AI = 아키텍처 상의 Slop**

![[바이브코더태동 1.png]]

- 에이전트에게 **"나를 부자로 만들어 줄 안드로이드 앱을 만들어 줘. 물론 오류는 없어야 해."** 라고 요청한다고 해서 완벽하게 작동하는 앱을 받을 수 있는 것은 아님
- 대부분의 경우 받게 되는 것은 **AI Slop**
- **Slop**: 코드뿐만 아니라 **AI가 생성한 콘텐츠 전반**을 일컫는 용어
    - 겉보기에는 그럴싸하게 작동하는 것처럼 보이지만
    - 실제로는 **품질이 떨어지거나 내부 구조가 부실한 결과물**
- 코드에서는 이런 문제가 더욱 두드러짐
    - 특정 상황에서는 앱이 정상적으로 작동할 수 있음
    - 하지만 내부적으로는 **구식 라이브러리**가 사용될 수 있음
    - **Android Studio 버전 간 호환성 문제**가 있을 수 있음
    - 코드가 마치 **다섯 명의 서로 다른 사람이 제각각 작성한 것처럼 뒤죽박죽**일 수 있음
    - 결과적으로 **유지보수가 어려운 코드**가 됨

## **실용적인 바이브 코딩**

- AI의 **빠른 속도와 유용한 기능을 활용**하면서도 **우리가 주도권과 통제력을 유지**
- AI가 생성하는 결과물을 **우리가 직접 제어**

## **코드베이스 가드레일 정의하기**

- AI가 **무엇을 다룰 수 있고 무엇을 다룰 수 없는지** 설정
- AI가 사용할 수 있는 **라이브러리나 외부 도구** 등을 설정
- 단순히 AI에게 작업을 지시하고 결과를 무작정 내버려 두지 않음

## **모듈식 계획**

1. AI가 실제 구현에 착수하기 전에 **먼저 계획을 수립**
2. **계획을 검토**
3. 모델과 **피드백을 주고받음**
4. 계획과 피드백을 바탕으로 AI가 구현
5. AI가 생성한 결과물을 **직접 제어하고 확인**

## **지속적 자동 검증**

- **승인되지 않은 작업을 수행하는 상황은 피해야 함**
- 이상적으로는 다음 내용을 문서화해 두어야 함
    - 에이전트의 **특성과 역할**
    - 새로운 기능을 구현할 때 에이전트가 **따라야 할 방식**
    - 새로운 기능을 구현할 때 따라야 할 **아키텍처**
- 이 문서는 요청이 있을 때마다 **에이전트에 의해 자동으로 읽힘**
- 따라서 문서의 내용이 **항상 에이전트의 메모리에 상주**하게 됨

# Planning Mode - AI 에이전트를 실제 개발 과정에서 어떻게 통제할까?

![[스크린샷 2026-09-19 171250.png]]
- 에이전트가 작업을 실행하기 전에 **미리 계획을 세우는 것이 중요**
- `Planning mode`는 Unreal Engine뿐만 아니라 `Anti-gravity`, `Cloude code`, 다양한 Harness 시스템 등에서도 찾아볼 수 있음
- 작업을 기본적으로 **두 단계로 나눔**

## 1. 계획 단계 (Planning)

- 에이전트에게 특정 작업을 지시하되 **즉시 실행하게 하는 대신,** 먼저 앞으로 수행할 작업의 정의를 담은 **청사진(Blueprint)**을 생성
- 청사진을 생성한 뒤 **작업을 멈추고 사용자의 피드백을 기다림**
- 사용자는 이 단계에서:
    - 의견을 남길 수 있음
    - 내용을 수정할 수 있음
    - 내용을 추가할 수 있음
- 사람과 AI가 **청사진을 매개로 소통하며 협력적으로 검토**
- **합의에 이를 때까지** 계획을 검토하고 수정

## 2. 빌드-수정-검증 (Build-Fix-Verify)

- 에이전트가 작업을 시작하기로 합의하면 **빌드-수정-검증의 반복 과정**을 진행
- 에이전트는 전체 청사진이 완성될 때까지 **계획을 단계별로 실행하고 수정**
- 각 단계마다 멈춰서 다음을 확인
    - 앱 빌드
    - 테스트 실행
    - 기존 도구들과의 정상적인 연동 여부
- 문제가 발생하면 수정하고 다시 검증하는 과정을 반복

## 핵심

**코드를 작성하기 전에 작업 내용을 먼저 결정하고 검토할 수 있다는 점이 중요함.** 해당 에이전트는 진행 방식을 제안할 뿐, 최종 결정은 여전히 우리의 몫

# **MCP: 에이전트와 툴체인 연결하기**

![[스크린샷 2026-09-19 172945.png]]

- 에이전트에게 **더 많은 권한을 부여하고 싶다면 MCP를 활용**할 수 있음
- MCP(Model Control Protocol)는 **에이전트를 위한 USB-C와 같은 표준 규격**
- 사용 중인 **에이전트 시스템을 외부 도구와 연결**할 수 있음
- 쉽게 말해 **서드파티 도구를 위한 API이자 연결 통로**

## Figma MCP

- 디자이너가 전달한 Figma 디자인에 에이전트가 직접 접근하게 하고 싶을 때 사용할 수 있음
- 기존 방식:
    - Figma 페이지나 스크린샷 이미지를 에이전트에게 제공
    - 정보를 직접 전달해야 하므로 **비효율적**
- MCP를 사용하는 방식:
    - `"Figma MCP를 활용해 이 디자인을 연결해 줘"`라고 지시
    - Figma가 **치수, 여백, 색상, 이미지 등의 모든 정의를 에이전트가 즉시 사용할 수 있는 형식으로 자동 내보냄**
- 이를 통해:
    - **정보 해석의 오류를 줄일 수 있음**
    - 해당 도구가 무엇을 지칭하는지 파악하기 위한 **추가적인 비용이나 노력도 줄일 수 있음**

## Jira / Trello 예시

- Jira나 Trello 같은 **업무 추적 도구**와도 연결할 수 있음
- 예를 들어 버그가 접수되었을 때:
    - 담당자에게 `"Jira에 접속해서 10번 버그를 처리하라"`고 지시
    - 담당자의 시스템이 Jira에서 **해당 버그와 관련된 모든 정보를 자동으로 다운로드**
    - 버그 **재현 방법을 파악**
    - **이를 통해 개발자는 원인 규명 및 수정 작업을 즉시 시작할 수 있게 됨**

# AppFunctions: 앱 기능 노출
![[스크린샷 2026-09-19 173231.png]]
[https://developer.android.com/ai/appfunctions](https://developer.android.com/ai/appfunctions)

- MCP가 에이전트를 **외부 도구 및 서비스와 연결**해 주는 역할을 했다면,  
    `AppFunctions` 는 **에이전트가 사용자의 애플리케이션에 접근할 수 있도록 해주는 기능**
- 구글이 작년에 도입했으며, 현재 **개발 단계**에 있음

## `AppFunctions`의 역할

- 개발 중인 앱과 **기존 Android 운영 체제 간의 일종의 계약**
- `annotation`을 사용하여 앱의 **특정 기능을 외부로 노출**할 수 있음

## 예시: 메모 앱

메모를 작성할 수 있는 앱이라면 다음과 같은 기능을 외부로 노출할 수 있음

- 새 메모 생성
- 메모 읽기
- 메모 검색

이렇게 기능을 노출하면 시스템에 다음과 같이 알리는 것과 같음

> "사용자가 음성 등으로 요청할 경우, 이 기능을 실행할 수 있다."

## 동작 방식

- 사용자가 새로운 노트 생성을 요청
- 시스템/에이전트가 어떤 기능을 호출해야 하는지 파악
- 해당 기능을 통해 앱의 **기능, 서비스, 데이터베이스 등**을 호출
- 결과적으로 에이전트가 앱의 기능을 활용할 수 있음

## 핵심 개념

- `AppFunctions`는 **중개자이자 API 계층**처럼 동작
- 애플리케이션과 에이전트 사이에 위치하여 **앱의 기능을 에이전트가 호출할 수 있도록 연결**
- 아직 **개발 및 실험 단계**
- 사용자가 **에이전트와 애플리케이션을 상호작용하고 연결**할 수 있게 한다는 점에서 강력하고 흥미로운 기능

# Agent Skills

![[스크린샷 2026-09-19 174119.png]]

![[스크린샷 2026-09-19 174455 1.png]]

- **Agent Skills**를 활용하여 에이전트에게 더 많은 기능이나 능력을 부여할 수 있음
- `Skill`은 **Anthropic이 만든 개방형 표준**
- 에이전트에게 **더 많은 기능이나 능력을 부여하는 방법**을 정의함
- 표준 자체는 매우 간단하게 설계되어 있음

## Skill의 동작 방식

- 핵심은 **필요할 때마다 해당 Skill이 실행(Trigger)된다는 것**
- 에이전트에게 특정 작업을 수행하도록 요청했을 때
    - 해당 작업이 **Skill 정의에 포함되어 있다면**
    - 에이전트가 해당 Skill을 **불러와 실행**
- 즉, 모든 Skill을 항상 실행하는 것이 아니라 **요청한 작업에 해당하는 Skill이 필요할 때 실행됨**

# Agent Skills 활용 사례

![[스크린샷 2026-09-19 174719.png]]

새로운 기능을 추가할 때 사용하는 아키텍처는 여러 애플리케이션에서 **비슷한 형태**를 가짐

```
웹 API / 클라우드 서버 / 외부 소스
              ↓
        Data Source
              ↓ DTO
         Repository
              ↓
      Application Model
              ↓
          ViewModel
              ↓
          UI State
              ↓
         Compose UI
         
- 웹 API, 클라우드 서버 등 외부 데이터 소스가 있음
- 데이터 소스가 DTO(Data Transfer Object)를 Repository에 제공
- Repository가 데이터를 변환 및 처리하여 Application Model로 매핑
- Application Model은 ViewModel에 의해 참조됨
- ViewModel은 애플리케이션, 더 정확히는 특정 화면의 생명주기에 바인딩됨
- 화면은 Compose UI로 구현되며, ViewModel의 UI State를 읽어와 표시
```

## **반복되는 파일 생성 문제**

- 새로운 기능을 추가할 때마다 **비슷한 구조의 파일들을 반복해서 생성해야 함**
- 이를 번거로운 작업으로 보고 **Skill을 생성**

## **Skill의 역할**

- Skill 설명에 현재 아키텍처를 정의
- **현재 아키텍처를 기반으로 새로운 기능을 구현하는 데 필요한 모든 파일을 생성**
- 해당 화면이 `Jetpack Composer`를 사용하도록 정의
- 데이터는 `loading`, `data`, `error` 등의 상태를 포함하는 **`Sealed Class`**로 정의하고 `ViewModel`을 통해 노출

## 생성 단계

1. **Data Source** 생성
2. **Repository** 생성
3. **ViewModel** 작성
4. **Composer** 작성
5. **Unit Test** 수행

복잡한 기술적 내용이라기보다는 **새로운 동료에게 이 작업을 어떻게 설명하고 정의할 것인지에 대한 방식**

## 정리

- 프로젝트에 막 합류하여 **현재 프로젝트의 아키텍처를 잘 모르는 새로운 동료**에게 작업 방식을 설명하는 것과 비슷함
- 코드를 많이 작성하지 않고도 **프로젝트의 작업 방식을 정의할 수 있음**
- `references`에 샘플 애플리케이션이나 모든 데이터가 포함된 샘플 패키지를 추가하여 에이전트가 **실제 코드를 확인하도록 할 수도 있음**
- `references`가 없더라도 에이전트는 **나머지 코드베이스에 접근할 수 있음**

- 겉보기에는 간단한 작업처럼 보이지만 실제로는:
    - 최신 Gradle Plugin으로 마이그레이션
    - 호환되지 않는 의존성 문제
    - 원인 파악 및 해결 등의 문제로 어려움을 겪을 수 있음
- 이러한 기술을 활용하면 해당 작업을 **에이전트에 맡기고 충분히 검증된 결과물**을 얻을 수 있음

## Skill 관리

- 익숙한 인터페이스를 통해 **Skill을 관리**할 수 있음
- **현재 프로젝트에 특정 Skill을 추가하도록 설정**하면
- 에이전트가 **해당 프로젝트의 작업을 어떻게 수행해야 하는지 파악**할 수 있음

# Rules와 Skills의 차이

![[스크린샷 2026-09-19 180101.png]]

| Feature      | [AGENTS.md](http://agents.md/) (Rules)             | [SKILL.md](http://skill.md/) (Skills)      |
| ------------ | -------------------------------------------------- | ------------------------------------------ |
| **적용 범위**    | Global (Every prompt)                              | Task-Specific (On-demand)                  |
| **목적**       | 아키텍쳐 & 가드레일                                        | 절차적 워크플로                                   |
| **컨텍스트 사용량** | 모든 세션/턴에 전달                                        | Progressive Disclosure를 통해 필요할 때 로드        |
| **대상 작업**    | 코드 스타일, 기술 스택, 사용 금지 사항                            | API 마이그레이션, 코드 감사, 프로젝트 설정                 |
| **핵심 역할**    | 프로젝트에서 항상 지켜야 할 기본 규칙 정의                           | 특정 작업을 수행할 때 따라야 할 **구체적인 절차** 정의          |
| **예시**       | Compose 사용, Hilt 사용, Repository 패턴, 특정 라이브러리 사용 금지 | API 마이그레이션, Compose 마이그레이션, 코드 감사, 프로젝트 설정 |

에이전트가 작업을 수행하는 데 필요한 **최소한의 정보만 항상 기억하도록 하는 것**이 중요함.

## Rules ([AGENTS.md](http://agents.md/))

- 에이전트의 MD에 정의된 **규칙(Rules)**
- **전역적으로(Global) 적용**
- 프로젝트를 수행하는 동안 항상 기억되는 정보
- **모든 세션과 요청마다 전달**됨
- 따라서 토큰이 계속 소모되므로 **꼭 필요한 내용만 포함**해야 함
- 주로 다음과 같은 내용을 정의
    - 아키텍처 관련 사항
    - 프로젝트의 기본 규칙 및 안전장치(Guardrails)
- 불필요한 내용을 많이 추가하지 않는 것이 좋음

## Skills ([SKILL.md](http://skill.md/))

- 에이전트에게 필요한 **역량(Capabilities)**을 정의
- 모든 요청에서 항상 읽는 것이 아니라, **현재 요청과 관련된 경우에만 로드**
- **온디맨드(On-demand)** 방식으로 동작
- 사용자가 Skill의 설명에 부합하는 작업을 요청하면 해당 Skill이 활성화됨
- 기존 프로젝트를 다루는 기본 규칙을 넘어, **특정 작업이나 과제를 수행하는 절차적 워크플로(Procedural Workflow)를 정의**하는 데 적합함

# 세션 격리

![image.png](attachment:7f79c248-7861-4665-b78d-4f9ba252df00:image.png)

## 세션을 독립적으로 유지

- 프로젝트 생성부터 기능 추가, 버그 수정 등 모든 작업을 **하나의 거대한 채팅 세션에서 처리하는 것은 권장하지 않음**
- 하나의 세션을 너무 오래 유지하면 시간이 지나면서
    - AI 에이전트가 이전 맥락 때문에 혼란을 겪을 수 있음
    - 환각(Hallucination)이 발생할 가능성이 있음
- 따라서 **새로운 기능, 버그, 새로운 상호작용을 시작할 때마다 기존 세션을 종료하고 새로운 세션을 생성**하는 것이 이상적

## 새로운 세션의 컨텍스트

- 새로운 세션에서는 **프로젝트의 메인 파일에 정의된 규칙만 최소한의 컨텍스트로 유지**
- 불필요한 이전 세션의 내용이나 기술, 정보를 배제
- 이렇게 하면
    - 요청마다 소모되는 토큰을 줄일 수 있음
    - 에이전트가 현재 기능 구현에 꼭 필요한 사항에 집중할 수 있음
    - 결과적으로 작업 효율을 높일 수 있음

**하나의 세션에 모든 작업을 계속 쌓기보다, 작업 단위로 새로운 세션을 시작하고 필요한 최소한의 컨텍스트만 유지한다.**

# Agent Loops
![[스크린샷 2026-09-19 183227.png]]

에이전트를 활용하면 상당히 많은 작업을 자동화할 수 있으며, 프로그래밍의 반복문과 유사하게 **사람과 에이전트 간의 상호작용을 중심으로 한 루프**를 사용할 수 있음.

## 1. 조건 기반 루프 (Term-based Loop)

- 사용자가 **“이제 됐다”라고 판단할 때까지 에이전트가 계속 작업**하도록 하는 방식
- 능동적인 사람의 상호작용이 필요함
- 시간이 오래 걸리는 작업을 에이전트에게 맡길 수 있음
- 새로운 기능이 구현될 때마다
    - 앱을 테스트하거나
    - 생성된 UI를 시각적으로 검사하는 등의 작업을 수행
- 사람이 **“이상 없음”을 확인한 후** 에이전트가 다음 기능 구현 단계로 넘어감
- 전체 아키텍처, 새로운 UI, 신규 테스트, 네트워크 연결 등을 포함하는 **대규모 기능 구현**에도 활용 가능

## 2. 자동 검증 루프

**각 단계나 새로운 파일을 작업할 때마다 에이전트가 다음 조건을 확인하도록 설정할 수 있음.**

- 앱이 정상적으로 컴파일되는지 확인
- CI가 정상적으로 작동하는지 확인
- 정적 분석을 경고 없이 통과하는지 확인
- 요청된 모든 새로운 기능이 제대로 작동하는지 확인

모든 조건이 충족되었을 때만 **목표를 달성했다고 판단**함.

- 이 과정에서는 사람의 개입이 필요하지 않음
- 조건이 충족될 때까지 에이전트가 스스로 작업을 반복

```
구현
 ↓
빌드 / CI / 정적 분석 / 기능 확인
 ↓
문제 있음?
 ├─ Yes → 수정 → 다시 검증
 └─ No  → 다음 단계
```

## 3. 프로액티브 루프 (Proactive Loop): 가장 중요

- 앞선 루프와 달리 **사용자가 특정 작업을 요청하지 않아도 에이전트가 자동으로 작동**하는 방식
- 타이머나 외부 트리거를 통해 실행할 수 있음
- 예:
    - 매일 밤 크론 잡(Cron Job)으로 자동 테스트
    - DAP…?(뭐지이게)가 정상적으로 작동하는지 확인
    - CI 상태가 Green(성공)인지 지속적으로 확인

### 오픈 소스 프로젝트 예시

```
사용자가 이슈 제기
      ↓
에이전트가 이슈 내용 파악
      ↓
자동으로 수정 가능 여부 확인
      ↓
수정 작업
      ↓
Pull Request 생성
      ↓
사람이 PR 확인 및 승인
```

- 에이전트가 사람이 요청할 때까지 기다리는 것이 아니라 **이슈를 트리거로 자동으로 작업을 시작**
- 최종적으로 사람이 `Pull Request`를 확인하고 승인하는 방식
- 이러한 방식이 팀으로 일할 때 익숙한 작업 방식이 되는 것을 목표로 함

# 적대적 코드 리뷰(Adversarial Code Review)

![[스크린샷 2026-09-19 184404.png]]
- 일반적으로 개발자는 **다른 사람의 확인 없이 작업 내용을 바로 병합하지 않는 것**이 중요함
- 자동화된 테스트, 정적 분석, CI 등을 활용할 수도 있지만, 팀에서는 항상 **다른 사람이 작업물을 검토**하도록 함

### 두 에이전트를 활용한 코드 리뷰

**적대적 코드 리뷰(Adversarial Code Review)**는 두 개의 에이전트를 활용하는 방식

```
첫 번째 에이전트
      ↓
개발자인 내가 직접 상호작용
      ↓
새로운 기능 구현
      ↓
테스트 코드 작성
      ↓
Pull Request(PR)
      ↓
두 번째 에이전트
      ↓
첫 번째 에이전트의 작업 검토
      ↓
PR에 리뷰 코멘트 작성
      ↓
첫 번째 에이전트
      ↓
리뷰 내용 확인
      ↓
답변 및 코드 수정
      ↓
팀원 간의 합의
      ↓
PR Merge
```

## 장점

- 두 번째 에이전트는 **첫 번째 에이전트의 작업 과정과 다른 깨끗한 관점에서 검토**할 수 있음
- 이 과정을 **자동화**할 수도 있음
- 에이전트에 대한 신뢰가 충분하다면 이전에 설명한 루프와 유사한 방식으로 반복 가능
- **서로 다른 기업의 에이전트를 활용**하여 이 과정을 수행할 수도 있음
- `Cloude Code` , `Gemini`

## 완전 자동화된 코드 리뷰

![[스크린샷 2026-09-19 185110.png]]
[이탈리아에 사는 제 친구가 만든 이 도구](https://github.com/hamen/pr-review-relay)는 기본적으로 에이전트가 자동으로 열 수 있도록 일련의 지침과 같은 구조를 생성합니다. 이 방식에서도 앞서 설명한 것과 같은 **루프(반복 과정)**가 진행됩니다.

```
첫 번째 에이전트
      ↓
코드 작성
      ↓
Pull Request(PR) 생성
      ↓
두 번째 에이전트
      ↓
PR에서 수정된 코드만 확인
      ↓
PR 탭에 리뷰 코멘트 작성
      ↓
첫 번째 에이전트
      ↓
코멘트 확인 및 코드 수정
      ↓
다시 리뷰
      ↓
(지정한 횟수만큼 반복)
      ↓
모든 리뷰 의견 반영
      ↓
최종 결과물 완성
```

- 두 번째 에이전트는 첫 번째 에이전트와 직접 대화하는 것이 아니라 **PR 탭에 코멘트를 남기는 방식**으로 리뷰함
- 사용자 없이 에이전트끼리 여러 차례 검토와 수정을 반복할 수 있음
- 반복 횟수는 **지정할 수 있음**
- 모든 검토 의견이 반영되면 최종 결과물이 완성됨

### 비용 측면

- 별도의 추가 구독이 필요하지 않음
- 기존에 보유한 구독 서비스를 그대로 활용할 수 있음
- 코드 작성과 코드 리뷰에 서로 다른 에이전트를 사용하더라도, **이미 지불한 고정 구독 비용 외에 추가 비용을 낼 필요가 없음**

## 기존 환경을 활용한 에이전트 자동화

- GitHub 등에 통합된 코드 리뷰 도구도 있지만, **별도의 비용을 지불해야 하는 외부 도구**일 수 있음
- 반면 이 방식은 **이미 컴퓨터에 설치된 에이전트와 개발 환경을 그대로 활용**할 수 있음

### 간단한 구현 방법

- 프로젝트 폴더의 **규칙(Rules) 파일에 해당 내용을 추가**하는 것만으로도 구성 가능
- 이를 통해
    - 두 개의 에이전트를 사용하거나
    - 동일한 에이전트의 서로 다른 두 모델을 사용할 수 있음

### 코드 리뷰용 모델

- 코드 작성 능력은 다소 떨어지더라도 **자동화 작업에는 충분히 좋은 상대적으로 저렴한 모델**을 사용할 수 있음
- 특히 에이전트가 **캐시(Cache)를 사용하지 않고 깨끗한 컨텍스트(Clean Context)를 사용하도록 지정**하면 적절한 코드 리뷰를 수행하기에 충분함

# AI 기능 측정: 안드로이드 벤치마크

![[스크린샷 2026-09-19 220902.png]]
- Google이 **GitHub의 오픈소스 저장소에서 가져온 100가지 작업**을 기반으로 만든 벤치마크
- Android 개발에 특화된 **AI 에이전트의 개발 역량을 구체적으로 측정**하기 위해 만들어짐
- 벤치마크 항목과 결과는 **주기적으로 업데이트**되므로 현재 내용은 [링크](https://developer.android.com/bench)에서 직접 확인하는 것이 좋음
- 특히 각 작업을 수행하는 데 필요한 **비용 정보도 확인할 수 있음**
- 따라서 Android 개발에서 AI 에이전트의 **성능과 비용을 함께 비교·확인할 수 있는 자료**

## 오픈 웨이트 모델

- 평균적인 비용의 모델뿐만 아니라 **성능이 괜찮으면서 가격이 훨씬 저렴한 모델**도 있음
- 다양한 모델이 존재하며, 벤치마크 목록에는 스크린샷에 담지 못한 모델도 더 많이 포함되어 있음

### 오픈 웨이트(Open Weight) 모델이란?

- 모델의 가중치를 공개하여 **자신의 컴퓨터에서 직접 실행할 수 있는 모델**
- 별도의 API 사용 비용 없이 사용할 수 있다는 장점이 있음
- 다만 로컬 환경에서 직접 실행하기 때문에 **실행 속도가 느릴 수 있음**
- 성능은 상용 고성능 모델보다 떨어질 수 있지만, **무료로 사용할 수 있다는 장점**이 있음

### 활용 관점

- 오픈소스 프로젝트나 개인적인 작업처럼 전문적인 업무가 아닌 경우에는
    - 반드시 가장 뛰어난 모델만 사용할 필요는 없음
    - 충분한 성능을 제공하는 무료 모델을 활용해 볼 수 있음
- 작업의 중요도와 목적에 따라 **고성능 유료 모델과 저비용·무료 모델을 적절히 선택**할 수 있음

# Q&A

## **스킬 문서는 직접 손으로 작성하시나요, 아니면 AI에게 생성을 맡기시나요?**

- **대부분 에이전트에게 새로운 Skill의 초안을 작성하도록 맡김**
- 생성된 초안을 직접 검토한 뒤 **필요한 내용을 보강하고 수정**하는 방식으로 작성
- Skill은 코드베이스를 전혀 모르는 **신규 동료에게 업무 흐름을 설명하듯이** 작성하는 것이 중요함
- Skill은 코드베이스 작업뿐만 아니라 사진 현상, 음향 처리 등 **에이전트가 미리 알기 어려운 특정 기술이나 워크플로를 정의하는 데도 활용 가능**
- 생성 결과는 Markdown 파일이므로 **에이전트가 작성한 후 사람이 직접 내용을 검토하고 수정할 수 있음.** 따라서 직접 처음부터 작성하기보다는 **에이전트에게 초안 작성을 맡기고 사람이 보완하는 방식**을 주로 사용함

## **AI 에이전트에서 다양한 Skill을 활용하는 것과 Skill을 최소화하거나 배제하는 것 중 어떤 방식이 더 효과적인가?**

- **정말 필요한 Skill만을 설치**하는 것이 좋음
- 요청 내용이 Skill의 설명과 일치할 때만 해당 Skill이 활성화되므로, 여러 Skill을 갖고 있어도 일반적으로 큰 문제는 없음
- **Skill 간 충돌이 없다면 프로젝트에서 활용 가능한 Skill을 여러 개 갖춰두는 편이 좋음**

### 직접 겪어봤던 스킬 충돌 사례

- 최근 폴더블 기기 지원을 구현하는 과정에서
    - Google의 새로운 **Adaptive Navigation 공식 컴포넌트**를 사용하는 방식
    - 기존 Navigation 방식을 사용하는 방식
    - → 에이전트가 어떤 방식을 사용할지 판단해야 하는 상황 발생

이 2가지가 존재해 스킬이 충돌한 적이 있음.

- 이 경우 에이전트가 어떤 방식을 사용할지 물어볼 수 있음
- **서로 충돌하는 Skill이라면 하나를 제거하고 하나에 집중하는 것이 좋음**
