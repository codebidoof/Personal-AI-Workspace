'Hoisting'은 '끌어올리다'라는 뜻이다. 컴포즈에서는 **컴포저블 내부에 있는 상태를 그 함수를 호출한 부모 컴포저블로 옮기는 것을 의미**한다.

컴포저블 안에  `remember { mutableStateOf(...) }` 를 넣어두면 그 컴포저블은 '상태를 가진(Stateful)' 컴포저블이 됩니다. 하지만 이런 방식은 몇 가지 단점이 있다.

1. **재사용성 하락:** 상태가 특정 컴포저블 안에 갇혀 있으면, 다른 화면에서 똑같은 UI를 쓰고 싶어도 다른 데이터를 넣기가 어렵다.
2. **테스트의 어려움:** 외부에서 상태를 마음대로 주입할 수 없어서 UI 테스트가 힘들어진다.
3. **단일 진실 공급원(SSO) 위반:** 똑같은 데이터를 여러 컴포저블이 각자 들고 있으면 서로 값이 어긋날 확률이 높다.

그렇기 때문에 컴포즈에선 반드시 `State Hoisting`이라는 개념을 사용해야 한다!

상태 호이스팅을 적용하면 컴포저블은 다음 두 가지 형태를 띠게 된다.
- **값(State)**: **부모가 자식에게 파라미터로 전달**합니다. (Data Flows Down)
- **이벤트(Event)**: 자식은 값이 바뀌어야 할 때 **부모가 준 함수를 호출**합니다. (Events Flow Up)

예시는 다음과 같다.
- State Hoisting 적용 전
```kotlin
// 이 MyInput은 자기 혼자만 데이터를 알고 있습니다. 부모는 이 입력창에 뭐가 써 있는지 알 길이 없습니다.

fun MyInput() {
    var text by remember { mutableStateOf("") } // ❌ 상태가 내부에 고립됨

    TextField(
        value = text,
        onValueChange = { text = it }
    )
}
```

- State Hoisting 적용 후
```kotlin
// 이 MyInput은 어떤 글자를 보여줄지, 글자가 바뀔 때 뭘 할지를 **외부에서 결정**해주는 대로 따르는 '순수한 부품'이 됩니다.

// 1. 상태를 관리하는(Stateful) 부모 컴포저블
@Composable
fun MyScreen() {
    // 부모가 상태를 딱 하나만 가지고 관리합니다 (단일 진실 공급원)
    var nameState by remember { mutableStateOf("") }

    Column {
        Text(text = "입력된 이름: $nameState")
        
        // 부품에게 상태와 '바꾸는 방법'을 전달합니다.
        MyInput(
            name = nameState,
            onNameChange = { nameState = it }
        )
    }
}

// 2. 상태가 없는(Stateless) 부품 컴포저블
@Composable
fun MyInput(
    name: String,                   // 보낼 데이터 (값)
    onNameChange: (String) -> Unit  // 알릴 통로 (이벤트)
*) {*
    TextField(
        value = name,
        onValueChange = onNameChange
    )
}
```

이렇게 State Hoisting을 적용하게 된다면 다양한 장점이 있다.

1. **결합도 낮추기**: `MyInput` 은 이제 `nameState` 가 어디서 오는지 몰라도 된다. 그냥 시키는 대로 그릴 뿐이다.
2. **상태 공유**: 부모가 가진 `nameState` 를 다른 컴포저블(예: 텍스트 뷰, 이미지 등)에도 동시에 뿌려줄 수 있다.
3. **가로채기 가능**: 부모 컴포저블에서 `onNameChange` 가 일어날 때, 특정 글자를 필터링하거나 글자 수를 제한하는 로직을 쉽게 넣을 수 있다.
4. **유지보수 용이**: `onNameChange`를 부모에서 정의해뒀기 때문에 비즈니스 로직이 변경되더라도 부모의 코드만 변경하면 되어 유지보수가 편리해진다.
