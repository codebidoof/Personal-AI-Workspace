전통적인 안드로이드 View나 **액티비티의 생명주기는 매우 복잡**하지만, 컴포즈의 생명주기는 훨씬 단순하다. 컴포저블은 `Composition(컴포지션)`이라는 구조 안에 들어오고, 머물고, 나가는 세 가지 단계만 기억하면 된다.

![[컴포저블 생명주기.png]]

컴포저블의 일생은 다음 세 과정으로 요약된다.

- **Composition 시작 (Enter)**: 컴포저블 함수가 처음 실행되어 화면에 나타나는 단계입니다. (탄생)
- **Recomposition (재구성)**: [[상태 호이스팅|데이터(상태)가 바뀌어서 화면을 업데이트]]하기 위해 함수를 다시 실행하는 단계이다. (변화)
- **Composition 종료 (Leave)**: 컴포저블이 더 이상 필요하지 않아 화면에서 사라지는 단계이다. (소멸)

예시 코드는 다음과 같다.

```kotlin
Column(
    modifier = Modifier.fillMaxSize(),
    horizontalAlignment = Alignment.CenterHorizontally // 가로축 정렬 (좌/우/가운데)
) {
    Text("첫 번째 줄")
    Text("두 번째 줄")
}
```

위 코드의 컴포지션이 종료되면 아래와 같은 그림처럼 배치가 된다.

![[이잉.png]]

이때 **리컴포지션**은 상태가 **바뀔때마다** 함수가 **처음부터 끝까지 다시 실행**된다. 즉, 상태가 바뀌면 화면을 다시 그리게 되는데 다양한 특징이 있다.

- **지능적 재구성 (Smart Recomposition)**: 컴포즈는 똑똑합니다. 화면 전체를 다 그리는 게 아니라, 상태이 바뀐 컴포저블만 골라서 다시 실행합니다.
- **실행 순서는 보장되지 않는다**: 여러 컴포저블이 있을 때, 컴포즈는 성능 최적화를 위해 실행 순서를 마음대로 바꿀 수 있습니다. 따라서 **"A가 먼저 실행된 후 B가 실행되겠지?"라고 가정하고 코드를 짜면 안 됩니다.**
- **병렬 실행 가능**: **컴포즈는 여러 스레드에서 동시에 함수를 실행할 수 있다.** (함수 내부에서 전역 변수를 수정하는 등의 '**부수 효과**'를 조심해야 하는 이유입니다.

위 3가지 특징을 한번에 보여지는 코드와 이미지는 다음과 같다.
```kotlin
@Composable
fun LoginScreen(showError: Boolean) {
    if (showError) {
        LoginError()
    }
    LoginInput() // 이 호출 지점은 Composition 내에서 LoginInput이 배치되는 위치에 영향을 미칩니다.
}

@Composable
fun LoginInput() { /* ... */ }

@Composable
fun LoginError() { /* ... */ }
```

![[로그인컴포저블 1.png]]

코드 내용대로라면 `LoginError`가 `LoginInput` 아래에 생겨야 맞는 것 같지만 컴포즈는 실행 최적화를 위해 순서를 마음대로 바꾸게 된다.

그렇다면 컴포즈가 "어떤 컴포저블이 바뀌었는지" 어떻게 알 수 있을까?

- **호출 지점(Call Site)**: 컴포즈는 컴포저블 함수가 호출된 위치를 보고 각 컴포저블을 구분한다
- **동일한 위치, 다른 데이터**: 만약 `Row`안에서 `Text` 를 여러 번 호출한다면, **컴포즈는 호출된 순서대로 이들을 식별**합니다.
	- 그런데 만약 리스트의 순서가 바뀌거나 중간에 아이템이 추가될 때, 컴포즈가 혼란을 겪지 않도록 `key`라는 값을 주어 "얘가 아까 그 애야!"라고 명확히 알려줄 수 있다.

```kotlin
@Composable
fun MoviesScreenWithKey(movies: List<Movie>) {
    Column {
        for (movie in movies) {
            key(movie.id) { // Unique ID for this movie
                MovieOverview(movie)
            }
        }
    }
}
```
